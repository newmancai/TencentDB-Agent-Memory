# B+E 第二轮产品优化：真实仓库试验与默认路径调整

试验于 2026-09-13 启动，2026-09-14 完成。已跑完四个真实仓库上的十二项顺序任务，
共 24 次 Codex 编码 CLI 运行。原话组与编译记忆组均 12/12，通过率没有差异。
本轮因此把产品默认改为直接保存原话，同时交付统一 CLI、实时日志、取消清理、差异审阅，
并修复“其余不变”缺少前文引用的问题。仍未证明稳定 B 收益或达到完整编码产品对标目标。

## 1. 任务、对照与结果

这次使用真实仓库和真实现有 API，任务是人为编写的维护场景，不是用户自然提交的 issue，
也不是官方 benchmark。每个仓库三步：按纠正后的策略添加 helper；添加同主题但必须维持
不同默认值的兼容 helper；收到第二次纠正后更新策略并添加后续 API。

| 项目及固定源码 | 任务重点 | 原话组 | 编译记忆组 |
| --- | --- | ---: | ---: |
| [boltons](https://github.com/mahmoud/boltons/tree/961dcff3f42e73b245aef65e377fe82763b257bb) | 文件名 slug、Unicode 与兼容默认值 | 3/3 | 3/3 |
| [more-itertools](https://github.com/more-itertools/more-itertools/tree/9ed3dbb0ae527230cd156d91d0af305478558fba) | strict 默认值、惰性迭代、兼容包装 | 3/3 | 3/3 |
| [packaging](https://github.com/pypa/packaging/tree/10590c194edb33c82f84a127883d6097c56b7840) | 版本尾零、非法版本与兼容策略 | 3/3 | 3/3 |
| [itsdangerous](https://github.com/pallets/itsdangerous/tree/672971d66a2ef9f85151e53283113f33d642dabd) | 有效期、显式零与异常传播 | 3/3 | 3/3 |

原话组直接保存相同用户消息，不运行编译器。记忆组显式编译并读取持久化约束视图。
各臂的代码工作区和 MemoryCore 状态独立，从同一初始 commit 开始，前一步编辑与历史保留
到后一步。检查器位于工作区外，不进入代理提示；开始前实核旧 API 通过、新功能缺失会失败。

配对结果为 **0 胜、0 负、12 平**，其中必要更新 8 平、同主题控制 4 平。
没有执行失败；针对性检查未发现既有 API 回归。检查不是各仓库的完整测试套件，不能据此
宣称所有严重回归都已排除。后续检查是累计检查，前一步失败可能影响后一步，十二题不独立。

请求模型为 `gpt-5.6-sol`、medium；CLI 未暴露可独立确认的 served model ID。
这比较的是受控 Codex 内部的原话与编译记忆，不能当成对原生 Codex 全部配置的产品胜负。

Claude 默认模型和显式 Sonnet 各进行了 45 秒诊断，均出现连续 HTTP 502，未取得回答。
其工作区已准备，但质量任务没有运行。没有把服务失败算成质量差，也没有填成四臂完成。

## 2. 成本没有支持默认编译

以下均为实测累计量。输入 token 包含编码 CLI 的多个内部轮次，不能与一次上下文字节数等同。

| 指标 | 原话组 | 编译记忆组 |
| --- | ---: | ---: |
| 编码 CLI 次数 | 12 | 12 |
| 额外约束编译 CLI 次数 | 0 | 12 |
| 编码输入 token，含缓存 | 2,803,371 | 2,452,353 |
| 编码缓存输入 token | 2,507,520 | 2,172,672 |
| 编码输出 token | 39,787 | 34,828 |
| 加上编译的全部输入 token | 2,803,371 | 2,629,487 |
| 加上编译的非缓存输入 token | 295,851 | 435,567 |
| 记忆／历史上下文字节累计 | 13,507 | 15,638 |
| 各任务完整耗时累计，含编译、存储和 checker | 1,323.672 秒 | 1,347.321 秒 |

编译本身用了 177,134 输入（其中缓存 21,248）、1,886 输出、115.620 秒。
总输入减少并不等于账单减少：非缓存输入反而增加，编译视图的字节数也更大。
美元费用未暴露，继续记 null；不按猜测价格估算。

本轮第一／第三步总是原话先跑，第二步记忆先跑，项目之间最多两个并发。这不是完整交叉
平衡设计，因此时延和缓存差异不能作因果解释。后续生成器已增加按项目交替的顺序偏移，
原始 manifest 保留旧顺序，没有把修改后的安排写回历史结果。

**产品决定：`remember` 默认只保留原话，不调用模型；实验性编译改为 `remember ... --compile`。**
没有编译约束时，scoped 也直接使用原话，不增加空结构包装。这消除了默认写入时不必要的
模型调用，不代表证明了所有场景下原话永远优于结构化记忆。当前十二题已出现基线满分，
本试验本身无法证明更难、长历史任务中的收益。

## 3. 发现并修复的真实记忆缺口

检查完成后的状态发现：more-itertools 和 packaging 的编译器把多个要求放进同一 key，
后续更新又沿用这个 key。当前视图只保留最新引文，例如“默认值改回 True，其他规则不变”。
被替换的原文仍在数据库，但没有进入上下文，解释“不变”所需的具体旧条款可能缺失。

编码任务仍通过，不能证明记忆视图完整：这些任务保留了此前已经实现的代码，模型还可以
从代码恢复规则。这个缺口在更换 worktree 或从旧代码继续时更可能暴露，但尚未实际量化。

修复现在沿已绑定的 supersedes 链提供 `predecessorEvidence`：

- 当前有效规则仍只有一条；旧引文明确标为 historical，不重新激活。
- 历史引用按来源顺序排列，使“其余不变”有前文可查。
- 整条更新链作为一个预算单元；装不下则走原话回退，不悄悄丢祖先。
- 损坏或跨 key／范围的链回退，且不返回部分已选 ID。

修复先在独立工作区完成测试，全部编码试验结束后才合入。对上述两个真实状态进行只读检查，
各恢复两条前任引文，当前有效规则数量仍各为一。**它没有参加表中的 24 次质量运行，不能把
12/12 当作修复后的质量成绩。** 未在已用题目上调编译提示词或重跑追分；还需要新任务检验
这项引用补全对代码质量、注入风险和上下文成本的实际影响。

这也不解决所有语义问题：如果模型没有正确绑定前任，或 key／范围本身判断错误，仍不能
靠机械引用校验保证正确。默认原话保留与显式选择编译因此仍有必要。

## 4. 交付的产品能力

- **统一入口**：包内提供 `memory-agent`，运行时与 benchmarks 解耦；源码也可运行
  `node bin/memory-agent.mjs`。需要 Python 3.10+、Node 22.16+ 和对应已登录 CLI。
- **实时日志**：模型原始事件直接写到运行目录，任务未结束也可查看。
- **取消行为**：超时／Ctrl-C 清理本次独立进程组，保留部分输出与 cancelled 状态，避免后台继续编辑。
- **可审阅差异**：保存相对 HEAD 的变化，覆盖普通新增文件；明确包含原有编辑，遗漏项单列。
- **真实顺序运行器**：按项目／实验臂保留状态和代码，分别记录提议成本、编码成本与完整操作时间。

本地打包提取后，在不包含 benchmarks 的包中验证了默认记忆写入、编码—checker 流程和
新增文件差异。这个打包测试使用模拟后端，依赖复用现有 node_modules，不是模型质量测试，
也不是全新机器安装测试。没有发布 npm 包或启用生产。

验证：20 项 Python 测试通过；隔离工作区全量 TypeScript 204 项通过，随后补充的损坏链
回退由相关 3 项测试通过；合入后插件构建通过。只读真实状态检查没有调用模型。

## 5. 接下来值得投入的方向

这轮已经把“能不能在真实仓库里贯通流程”推进了一步。下一轮应转向真实缺陷修复、跨文件
迁移、较长历史中的条件和撤销，避免继续用短、明确的 helper 任务堆数量。开发阶段定位
普通读取的失败机制，再在独立、完整的新项目留出上比较，不只报告事后筛出的失败子集。

对照保留原生正常配置、同信息原话／普通检索、确定性状态处理和必要时的编译。所有记忆
收益都应计入前置处理和后续生成总成本；下一轮不使用本次十二题调提示词或证明泛化。
CLI 还需长任务恢复、长期容量管理与真实安装验证；默认 128 条观察和单写者仍是原型边界。
