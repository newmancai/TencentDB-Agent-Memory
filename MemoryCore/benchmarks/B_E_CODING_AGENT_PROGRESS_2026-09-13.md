# B+E 向编码代理产品推进：当前成果与优化判断

日期：2026-09-13。目标是达到 Codex／Claude Code 一类编码代理的交付体验和可靠性。
本轮已实现可运行的持久化项目记忆 CLI，并完成真实 Codex 工具调用的顺序集成验证。
当前阶段是实验原型，尚未达到同级产品，也尚未证明 B 的稳定净收益。

## 1. B 和 E 分别到了哪里

| 维度 | 当前已实现 | 仍缺少的证据或能力 |
| --- | --- | --- |
| B：理解反馈并影响未来行为 | 用户原话保留；固定提示词生成带来源的约束提议；路径、动作、顺序和同范围前任约束；保留普通原话强基线 | 范围判断和语义 key 仍可能出错；没有跨真实项目的稳定净收益；没有证明优于普通读取的学习策略 |
| E：把状态用于真实执行 | 原生 SQLite 保存；历史视图、撤销；跨进程恢复；上下文送入编码 CLI；文件编辑后独立 checker；执行证据回写 | 当前单写者、有容量限制；缺少长期任务恢复、跨设备同步、成熟权限体验和真实使用可靠性 |
| 编码执行 | Codex 完成真实工具调用、修改文件和后续任务；Claude 适配与服务诊断已接入 | Claude 本轮连续 502，未完成编码任务；尚无两产品完整四臂结果 |
| 产品结论 | 用户可以在源码检出上使用 remember/context/run/history/retract | 不是独立安装发行版；不是完整 IDE/终端产品；不能宣称达到产品对标目标 |

因此，B 的研究交付完成、E 的组件闭环完成，与用户能长期依赖的编码产品完成，是不同层次。
新原型把研究和真实编辑连接起来，尚没有跨过稳定收益与产品可靠性这两道门槛。

## 2. 本轮直接做了什么

### 项目记忆核心

新增 `ProjectMemory`，复用现有 MemoryCore L1／SQLite，不改 Gateway：

- 保存完整用户观察和可追溯引用；只有 user 来源可提出规范性约束。
- 约束带路径和动作范围、来源 ID、宿主分配的单调顺序。
- 仅允许显式替换同 key、同范围的当前前任；API 的变化不能覆盖 worker 的规则。
- 原始历史不删除；支持给定顺序之前的视图和显式撤回，撤回后不自动复活更旧规则。
- 查询目录时保留其子目录规则的明确范围；路径不明时默认查看整个项目而不猜测。
- off、预算遗漏、存储异常均显式记录；不把读取失败当成“没有历史”。

最后一点是测试中发现的实际问题。原生容错查询返回空数组，适合检索降级，却不能安全支持
有状态的“读取—修改—写回”。新增可选 `queryL1RecordsStrict` 能区分空数据与失败，原有
容错查询保持既有行为。尚未实现该能力的存储后端不能悄悄启用项目状态更新。

### 可运行的编码宿主

新增源码 CLI，把前一轮真实保存的状态送到后一轮编码任务。用户可保存纠正、查看上下文、
执行编辑和检查、查看历史、撤回约束。每次调用保留原始事件、提示词、usage、时延、checker
和记忆版本。提议失败保留原话；工具回执作为观察，不自动变成用户长期指令。

正常使用保留项目指导文件的自动发现；受控实验才关闭它们。MemoryCore 的 off 不应降低原生
产品正常读取项目规则的能力。当前 Claude 工具集合由此原型管理，因此“保留项目指导”也不能
等同于“完整原生产品配置”。

### 修复产品评测判定

原评测汇总可能在单题、缺乏控制题或两 backend 题集不同的情况下给出 pass。本轮改为核对
manifest 的完整四臂矩阵、重复回执、项目簇、簇内两类任务和最小题量。pilot／diagnostic
不能输出产品通过。超时先停止该调用的进程组再检查，防止残留代理边改文件边打分。
Claude JSON／JSONL usage 和终止错误已纳入处理，缺失成本继续记 null。

四臂文件 runner 仍接收外部提供的 context；它本身不证明记忆来自真实历史。本轮实际历史
链通过新的 CLI 与 sequence smoke 验证，不能把两者混称为已完成真实项目四臂评测。

## 3. 实际运行结果及其含义

新建一份此前未使用的合成 Python 仓库。先保存 API 默认 2／worker 默认 5 的用户指令，再
保存只把 API 改成 0 的纠正。每臂复制相同初始仓库和状态，之后独立持续执行三项任务：
实现 API 设置、实现 worker 设置、复用 API 设置实现后续预算函数。检查器在仓库外，未进入
代理提示；后面的检查也覆盖前面已完成的行为。

请求模型为 `gpt-5.6-sol`，medium；Codex 事件未暴露可独立确认的实际 served model ID。
两种配置均保留独立原始事件。这里的“调用”是 CLI 运行次数，编码运行可能包含多个内部模型轮次。

| 项目 | 普通原话 | 项目记忆 |
| --- | ---: | ---: |
| 检查通过 | 3/3 | 3/3 |
| 配对胜／负／平 | 基准 | 0／0／3 |
| 三题上下文字节总和 | 2,263 | 2,120 |
| CLI 累计输入 token，含缓存 | 308,711 | 274,418 |
| 其中缓存输入 token | 278,528 | 239,232 |
| 输出 token | 3,204 | 3,150 |

另有两次共享初始约束提议：28,971 输入、227 输出、17.434 秒；分别接纳两条初始约束和
一条有前任引用的更新。它们不能从记忆方案总成本里消失。普通原话无需这一步；本 smoke 为
验证相同历史与状态复制共享了提议后的种子库，表中把预处理成本单列。

**不能据此宣称省钱。** 普通原话的非缓存输入是 30,183，项目记忆为 35,186；再加预处理，
累计输入更少不等于实际账单更低。这里报告的时间统一只含 CLI，不含 SQLite 桥接与 checker。
后续宿主回执已补齐操作总时延与存储时延；没有把后加字段倒填成早期调用实测。

Claude 首次 120 秒未返回；第二次带流式日志的 45 秒诊断显示连续 HTTP 502、服务端重试，
尚无模型回答。不能把基础设施失败算成质量失败，更不能填成已完成的四臂结果。

这次验证支持：来源引用、持久化恢复、局部更新不误伤另一目录、后续真实编辑链正常。
**不支持：质量提升、稳定降本、真实项目泛化、商用可靠性或 Codex／Claude Code 产品对等。**

## 4. 要到同级成果，优化优先级如何改变

### 第一优先：在强执行底座上找到可重复的用户价值

先利用现有 Codex／Claude 的执行能力，集中解决“用户改过一次，以后在正确地方持续生效”
这个可检验的问题。小模型换提示词、把输出写得更像画像，并不能建立这项产品价值。
产品的第一条验收标准应是后续代码行为正确，而不是画像完整率或候选召回率。

接下来应构造至少四个真实项目簇、至少十二个顺序任务，每簇都有必须更新和困难同主题控制。
以项目为单位留出，固定基础提交与独立检查，禁止用已经观察过的项目题目调提示词后当新验证。
分别报告 Codex 内部和 Claude 内部的记忆增量；四簇十二题只是开始估计，不是充分统计把握。

对照至少保留：原生产品正常配置；同信息原话／普通检索；确定性范围与版本处理；加入学习的
记忆策略。当前的受控配置只回答 MemoryCore 增量问题，不能替代原生产品体验对标。四臂的
两种 clean 必须明确是原话强基线还是无历史消融，不能混用。

### 第二优先：先避免错误记忆，再减少无效处理成本

目前模型推断的范围与 key 仍可能错；机械引用校验不能判定整句是否在当前任务适用。尤其是
同名对象、目录例外、用户只修改某一种动作、撤销和条件语句，应作为新的困难控制。
对存在歧义的反馈保留可读原话与候选，不能把自动编译的结构包装成语义真值。

本 smoke 还提示一个成本问题：两条很短的用户输入，提议阶段已累计 28,971 输入 token。
下一步应比较不加工的原话、确定性显式指令和必要时才调用解释器的方案，计入解释、选择、
存储、检索及后续生成总成本。不能为了降低字节数，删掉尚未被结构化覆盖的原话要求。
只有更复杂的新任务证明共享策略比这些对照好，才值得扩大反馈学习。

### 第三优先：补齐编码产品的可靠交付体验

用户需要任务能完成、变更可审阅、失败可恢复。后续产品实现应围绕：长任务中断恢复、
差异预览和撤回、测试失败的可定位解释、稳定权限与工具交互、记忆查看与纠错、安装和升级。
在这之前，先把本原型从评测目录适配器依赖中拆出，提供单一安装入口；再替换每次启动 Node
桥接的方式，减少延迟，同时保留明确存储失败与进程隔离的行为。

128 条观察的整块状态适合当前原型；长期开箱产品需要事务化版本记录、容量与归档策略、
多写者冲突处理。不能把单写者文件锁称为分布式一致性。检索也不能永远只靠调用者指定路径；
应把项目结构、任务涉及的文件与用户原话结合，再用困难范围控制验证召回和误注入。

### 第四优先：用结果决定是否做学习，而不是预设必须训练

本轮没有新增可迁移的反馈学习收益。B 的最有价值后续问题仍是：在同一执行模型、相同
原始证据下，能否提高后续任务通过率，同时减少严重回归和总成本。如果普通读取和确定性
状态已经一样好，应直接产品化更简单的方案；若出现稳定失败模式，再针对那个模式学习。
